## 利用者からの要望（2026-11-09）
- **進捗表示**: スキャンと実行の進捗を、容量（バイト数）と件数（ファイル数）の両方で表示する。
  - スキャン: 計測済みのバイト数とファイル数。前回のスキャン結果（キャッシュ）を見込みの全体量として使う。
  - 実行: 処理済みのバイト数とファイル数 ÷ plan.json の予定量。コマンド型の行（`npm cache clean` など）は、対象フォルダーの残量を一定間隔で測って進捗とする。
  - 上の値から **経過時間 / 推定所要時間（elapsed / estimated）** を表示する。
  - 背景: 2026-11-09 の実行では `npm cache clean --force`（6 GB）に 10 分以上かかったのに、途中経過が何も出なかった。

## 優先度高：ページファイルの助言の誤り（2026-11-09 判明）
- 「ページファイル内の最大使用量（Win32_PageFileUsage.PeakUsage、2.8 GB）」を根拠に縮小を勧めていたが、これは誤り。
  - 判断の根拠にすべきなのはコミット済みメモリ（CommittedBytes）とその上限（CommitLimit = 搭載メモリ + ページファイル）。
  - この PC では、コミット済みメモリが上限の約 85% に達していた。システムログには仮想メモリ不足の警告（イベント ID 2004）が繰り返し記録されていた。
- probes の pagefile を、コミット済みメモリのピークと 2004 イベントをもとに判定するよう直す。
  - 足りなくなる恐れがあるときは「縮小しない」と助言する。
  - カタログの advice_ja も直す。
